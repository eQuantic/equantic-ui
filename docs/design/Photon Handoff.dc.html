03

Rules the build must not break

Engine fence (mobile)
  • Rounded rects, uniform borders, 2-stop gradients, rrect shadows, 2D transforms, shaped text, scroll — nothing else.
  • Icons are font glyphs or bitmap atlases. The engine never receives a path.
  • The Vector node conforms — arbitrary path data is rasterized once into a cached A8 texture by the same glyph rasterizer icons use, so what reaches the engine is a texture, i.e. the permitted bitmap-atlas case. Settled; do not re-litigate. What stays out is per-frame path drawing.
  • Blur only on overlays/sheets, and never required for legibility.
  • One shadow per node; disabled = 38% opacity group.
Non-negotiables (all platforms)
  • Touch targets ≥ 48dp even when the visual is smaller. OPEN QUESTION (v1.1): Density.Compact collapses the hit expansion to hit = visual height (§3b) — this rule either gains an explicit pointer-density exception or the SDK is in violation; unresolved in code.
  • Pressed feedback within 50ms of touch-down.
  • Every gesture action also exists as an a11y custom action.
  • Hover is pointer-only — never on touch — and clears when the pointer leaves the window (spec §10).
  • State is a STATE (aria-checked / SemanticNode field), never smuggled into the accessible name (spec §10).
  • No raw hex in component code — tokens only.
  • Light and dark ship together; no "dark later".
3b

API contract — read before you type

the names that look interchangeable and are not
Use
Why the plausible alternative is wrong
eQuantic.UI
.Primitives
The token core is Layer 1, shared by web and native. Filing it under .Native.Theming contradicts the rule it exists to enforce — never fork Layer 1 per platform.
no IsDark
The theme is mode-free. Web emits light-dark(light, dark) so a page renders once for both modes; native resolves when it paints. A theme that knows the mode forces SSR to know the user's preference. Resolve with token.Resolve(ThemeMode) at realize time.
IconSize.Sm 16
Dense 20
Md 24 · Lg 32
Same four-step ladder, SDK names. Relabelling it Sm/Md/Lg/Xl silently redefines IconSize.Md from 24 to 20 in existing code — visual drift with no compile error.
SizeVariant
A bare Size collides with SizeValue (the layout sizing type) at every call site.
full IAppTheme
Members specs may reference: SurfaceHighlight · FocusRing (not Focus) · LinkColor · DisabledOpacity · Shape(ShapeScale) alongside the Radius constants. Variant : byte has ten members with Tertiary last (= 9) — and Tertiary is not its own palette: it returns the Info five-tuple verbatim.
Sizing.*
(SizeVariant)
Never inline the control ladder. Sizing.Height · PaddingX · Gap · LabelSize · Icon · Radius · HitTarget — every control (button, field, select, menu row, chip, segmented, stepper) reads these instead of carrying its own numbers. ButtonStyles.Metrics(size, density) is a tuple view over the same seven. Touch floor is Touch.MinTarget = 48; XLarge is the only rung whose hit target is 56 (Comfortable — see the Density row).
Density
: byte
enum Density : byte { Comfortable = 0, Compact = 1 } is real and threads the control ladder: Sizing.Height / PaddingX / LabelSize / HitTarget(SizeVariant, Density density = Density.Comfortable) and ButtonStyles.Metrics(SizeVariant, Density = Comfortable); components read context.Density. The plausible-wrong: calling Sizing.*(size) alone and silently getting Comfortable (touch) sizing everywhere on desktop. Compact ladder, read from the SDK: heights 26/32/40/48 · padX 8/12/16/20 · labels 11.5/13/14.5/15.5. OPEN QUESTION — do not silently resolve: under Compact the SDK collapses the 48dp hit expansion to hit = visual height, contradicting §03; either §03 gains an explicit pointer-density exception or the SDK is in violation. Unresolved in code.
TypeRole
10 members
The scale no longer stops at Caption: TitleSmall = 7 (15/20 · Bold · −0.1 · ×1.3) · LabelSmall = 8 (11/15 · Medium · 0.1 · ×1.3) · Overline = 9 (10/14 · ExtraBold · 1.0 · ×1.2) — the dense desktop rungs (Theme/Typography.cs). TypeStyle also carries a trailing bool Mono = false — the monospaced face, on the STYLE so the measurer, rasterizer and raster cache all key on it. Plausible-wrong: assuming the scale stops at Caption and hand-shrinking Labels for sidebars.
SurfaceHighlight
is translucent
White at 55% (light) / 7% (dark) — the top-edge highlight over a surface, so it must composite over whatever sits beneath it (raised edges, the Skeleton shimmer). Decorative, no contrast requirement. An opaque value turns it into a solid bar.
Motion.Press
State · Enter
Exit
Motion is named, not numeric — spec an animation as Motion.Enter, never "300ms". Each role carries both halves: Press 100/standard · State 200/standard · Enter 300/decelerate · Exit 200/accelerate (= ExitFor(300)). Animate style changes with TransitionSpec.Of(StyleChannels.X, Motion.Y), which carries the curve; TransitionSpec.Colors() defaults to 100ms. The scale is 100 / 200 / 300 only — 150ms sits on no rung.
shadow alpha
pairs
Explicit per level: 0.10/0.45 · 0.12/0.48 · 0.16/0.52 · 0.20/0.56 · 0.26/0.62. Do not derive dark from light — it is +0.35 on level 1 and +0.36 on 2–5.
Color
byte alpha
The colour primitive is Color(byte R, byte G, byte B, byte A) + FromRgb · FromRgba · WithOpacity(float) · Transparent/Black/White. ColorToken(Color Light, Color Dark) has a one-arg ctor for same-in-both-modes. There is no Rgba type and no ColorToken.Of(uint,uint).
TypeStyle
arg order
TypeStyle(Size, LineHeight, Weight, Tracking, MaxScale) — LineHeight is second and Weight is the FontWeight enum (Regular 400 … ExtraBold 800), not an int. Display = new(34, 40, FontWeight.ExtraBold, −0.4f, 1.15f).
StyleChannels
TransitionSpec
: byte { None 0, Colors 1, Opacity 2, Transform 4, Shadow 8, Filters 16, Size 32, All 63 } — Opacity is 2 and Transform is 4, not the reverse; Filters (element + backdrop blur) and Size (width/height/max-bounds morph) are real channels. TransitionSpec(Channels, DurationMs = Motion.BaseMs, DelayMs = 0) with Easing init — it does not wrap a MotionSpec. Factories: Of · Colors · All.
springs: type
≠ behavior
Curve is exactly (X1,Y1,X2,Y2) with three beziers. Curve.Spring(…) and Motion.Settle still do not exist — but SpringSpec(float Stiffness, float Damping, float Mass) DOES exist now (Theme/Tokens.cs, SpringSpec.Default = (380, 34, 1)) and is consumed by NOTHING: no realizer reads it. Guidance unchanged — do not spec springs yet; the plausible-wrong is treating the type’s existence as shipped behavior. Gesture release (v1.1): the sanctioned interim is the Release glide — 200ms (Motion.BaseMs) smoothstep to the target picked at release; it lives in the gesture system, still not a Curve token. Spring BEHAVIOR stays REQUEST. Also: ExitFor(int) = enterMs * 2 / 3 (integer — 300 gives exactly 200) and the constant is ReducedCrossfadeMs.
members that
do / don't exist
DisabledOpacity is on IAppTheme (0.38f), never on Sizing. Space.Base does not exist — the scale is S1…S16 + Gutter. Touch.PressCancelSlop = 12 does exist. ButtonStyles.Metrics returns a named tuple — there is no ControlMetrics record.
gpp_maybe The rule behind every row above: never reconstruct an API from its description. If you cannot quote the real signature, write the need in prose and mark it a request. An invented member that looks plausible costs more than an honest gap, because it reads as verified.
Everything else in tokens.json — colors, spacing, radii, type roles, elevation, motion, the size ladder — matches the SDK exactly. Do not "improve" those values.

Live blocksREQUEST · live blocksroadmap 3.2

Every block on the phase pages draws its component. The playground already compiles C# with the real eqc on the server. The request: a block names its component and a snippet (suggested marker data-live="Button"), the page build compiles the snippet through that same path, and the result is mounted beside the drawing in both themes, linked to the tests and goldens that hold it.

What it buys. A block whose snippet stops compiling fails the build, so an API change cannot leave a drawing behind, and a designer reviews the control users get instead of a picture of it.
