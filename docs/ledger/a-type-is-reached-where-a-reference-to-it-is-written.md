- **2026-11-27 · A referenced project's type is reached where the module writes a reference to it**: a page
  that showed the app's own `Order` and named a referenced project's `Order`, a class that reads a file, only in
  a cast of a null, a `default`, a delegate's type, a constant in the old `is` form or a member of an enum nested
  in it, failed at the referenced project's file, though the module writes nothing of that `Order`. The module's
  `./Order` was mapped back by its name to every declaration the page's syntax names. Each writer of a twin's
  name now records the symbol it wrote it for (`WrittenTwins`): a construction, an annotation, a class's base, a
  static call or read, a reduced extension's home, a hydration spec, a union's cases. Where every use of a name
  in the module is a write on record, the import means those types alone; where a writer recorded nothing, it
  means what it meant before, so an unrecorded writer costs precision and never a type the module writes.
  `ImportsOnTheWalkTests` holds the imports still decided the old way in a baseline that may only shrink
  ([#830](https://github.com/eQuantic/equantic-ui/issues/830)). Proposed and archived through OpenSpec
  (`openspec/specs/referenced-projects`).
