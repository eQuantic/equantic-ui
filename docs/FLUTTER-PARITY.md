# Flutter, one row at a time

Flutter is the reference this SDK was inspired by, so "how does Flutter solve this?" is the first
question to ask when a design decision is open. This is the answer to that question across
Flutter's whole surface, measured against ours rather than remembered.

**It is not a to-do list, and parity is not the goal.** Three verdicts appear here, and the third is
the one that matters:

| | |
|---|---|
| **SAME** | we arrived at the same shape, usually for the same reason |
| **DIFFERENT** | we answer the need another way, deliberately, and the entry says what we traded |
| **GAP** | Flutter answers something we do not, and nothing here is a decision — just an absence |

A DIFFERENT row is not a smaller version of Flutter's answer. Several of them exist because this SDK
has a constraint Flutter does not: **a component is written once and realized on a DOM and on a GPU
display list**, so anything that needs one target's machinery cannot enter the vocabulary at all.

Its companion is [ARCHITECTURE-AUDIT.md](ARCHITECTURE-AUDIT.md), which asks the other half of the
same question: this file asks *how does Flutter solve this?*, that one asks *where is our own
structure weak?*. Both are measured rather than recalled, and both are pinned.

Measured against the tree at the time of writing; every claim below was grepped, not recalled — and
kept true by `FlutterParityPinTests`, which reads this file and probes all 76 rows. A SAME,
DIFFERENT or PARTIAL row must be findable in the public surface; a GAP row must still be missing;
and a row added without a probe fails the build. So the audit cannot rot, cannot gain unchecked
prose, and cannot go on claiming an absence that has ended.

## 1. Widgets and the internal trees

| Flutter | Here | Verdict |
|---|---|---|
| `Widget` — immutable configuration | `VisualNode` (a COMPONENT here; "widget" is Flutter's word and stays in this column) | **SAME**, including the part people find surprising: it has **no `Parent`**, deliberately. It is rebuilt constantly, so a back-reference on it would mean nothing. |
| `StatelessWidget` | `StatelessComponent` | **SAME** |
| `StatefulWidget` + `State` | `StatefulComponent` with `SetState` | **SAME** in shape. One class rather than two: Flutter splits them because a `Widget` must be immutable and `State` must persist, and our element keeps the retained instance instead, handing each fresh one's configuration to it through `AdoptConfig`. |
| `initState` | `OnMount` | **SAME**, with a narrower promise. It does **not** mean "the pixels exist" — Photon has no DOM to read geometry from, so a hook promising that could not be write-once. |
| `dispose` | `OnUnmount` | **SAME** — and it ships with `OnMount` rather than after it, because without the pair every mount is a leak. |
| `didUpdateWidget` | `AdoptConfig(UiComponent next)` | **SAME** |
| `didChangeDependencies` | — | **GAP**, and it follows from the Element row below: with no dependency graph there is nothing to be notified about. |
| `InheritedWidget` / `InheritedModel` | `GetService<T>()` over a `CapabilityScope` | **DIFFERENT.** Ours is AMBIENT, not positional: resolution walks a scope, not the tree. The trade is real and worth stating — no per-position override (two subtrees cannot see different values of the same thing) and no dependency-driven rebuild (changing a value does not invalidate the components that read it). What it buys is that a component never has to be handed a context to read the theme. |
| `Element` tree, `BuildContext`, `BuildOwner` | `Element` (`ComponentElement`, `NodeElement`) and `BuildOwner` | **PARTIAL, and the structural one.** On Photon the tree exists since E1 (#950): an element per node, kept across frames, a stateful instance retained by its element, and a build phase before layout that builds only what is dirty, ancestors first, as `buildScope` does. Since #975 what a node keeps between frames (a scroll offset, a drag, a transition's tracks, a presence's entrance, an `InView`'s last report) lives on its element too, as a `State` lives on Flutter's, and leaves with it. Since #976 the host finds a node by its element: the press, the focus, the field being edited and the hover follow the position and never pass to a node that takes its place, and a frame after input builds what its handlers marked with `SetState`. Since #996 a field keeps what was typed on its position, as `EditableText` keeps it in its controller, and shows what the page holds when the page builds it again, as a controlled field's `didUpdateWidget` sets the controller; so a key builds what the field's handler marked and nothing else. A code surface's or a spreadsheet's handler that calls no `SetState` still gets a frame that rebuilds everything, because the host cannot see which component shows what their models hold. Of the two halves that were missing, one is done: since E4a (#1450) the server draws a page through an owner for the request, and since E3b-1 (#1453) the browser builds through the engine's owners, so no target keeps instance handling of its own. The other is under way: since #1412 a component position has a context of its own that reads its frame from the owner and finds the inherited values above it, while `Theme.of(context)` and the route as inherited values are E5b's (#1395). The rows above and below it that trace here close with those slices ([ELEMENT-TREE-PLAN.md](ELEMENT-TREE-PLAN.md)). |
| `RenderObject` with `parent` | `LayoutNode` with `Parent` | **SAME.** Flutter makes this tree bidirectional and its configuration tree not; so do we, for the same reason. |
| `parentData` | — | **DIFFERENT, and needs nothing.** It exists to carry what a parent assigned — an offset, a flex factor — and this engine resolves all of that into `Bounds` in the same pass. A second slot would hold a copy. |
| `RenderSliver`, viewport virtualization | `ListView` (builds only the visible window plus overscan) | **PARTIAL.** The capability is there; the protocol is not. v1 fence, stated in the code: vertical only, fixed `ItemExtent`. There is no general sliver contract other nodes can implement; two axes have a viewport of their own (the `TableViewport` row below). |
| `ReorderableListView`, `Draggable`, `DragTarget`, `onReorder` | `Sortable` and `SortableItem`, reporting a `SortDrop` | **PARTIAL.** The shape is dnd-kit's and the duties Flutter's: the drop is the app's to apply (`onReorder` never reorders behind the app's back), a guard is asked before a place is offered (`onWillAccept`, here `Accepts`), and the hover is reported (`onMove`, `onLeave`, here `OnHovered`). It goes further where Flutter leaves the app alone (#1535): one node pair sorts inside a list AND across the lists of a group, the index is computed by the realizer from the items' boxes, and nesting is a flag, where Flutter's app composes `Draggable` and `DragTarget` and measures each target itself. It also sorts by the keyboard, each step said to a reader (#1536), which Flutter's reorderable list leaves to its drag handle's focus. Photon carries an item the same way, by one arithmetic both targets run (`SortPlacement`, #1537). A `TreeView` moves its nodes on it (#1533): Flutter's `TreeSliver` has no drag and leaves each app to compose one per row, where the tree reads a drop as the node, its new parent and the sibling it lands after, and the keyboard steps through the places inside a nesting list's items. Between the end of a subtree and the next row the depth is chosen too (#1594): a list whose items have depths reads it from the pointer's travel across, one level per indentation, as dnd-kit's sortable tree projects it, and from the keyboard's cross arrows, so a node can land as the last child of an open folder. The lifted item's look is the theme's `SortableTheme` with the list's own `style` over it (#1602), where Flutter's app wraps the dragged item in a `proxyDecorator`: a theme sets it once for every list, and the copy's shadow is a level of the theme's elevation scale, as Flutter's default lifts on a `Material` at the theme's elevation. Each step is said in the words the list carries (`SortAnnouncements`, #1564), the SDK's in the reader's language unless the app gives its own, where Flutter's localizations reach a widget through its context: Photon speaks them through a live region, as the web does. PARTIAL because on Photon a focused item does not describe the keys yet (#1596). The web's drags, `Draggable`'s, `DragDismiss`'s and this one, run on one gesture core. |
| `DataTable`, `DataColumn`, `DataRow` | `DataTable`, `DataColumn`, `DataRow` | **SAME, and further.** The shape is Flutter's: columns and rows the app hands over, a sort the heading reports (`onSort`, here `OnSort`) and the app applies, and a selection the app keeps. Flutter's table stops there: its widths are a `TableColumnWidth` the app fixes, and an app that lets a person reorder or resize the columns composes the drag itself, as `pluto_grid` and `syncfusion_flutter_datagrid` do. Here the table composes the vocabulary's own nodes (#1538): the header row is a horizontal `Sortable` of its headings, by pointer and by keyboard, and a column whose width is a number has an edge a pointer drags and the arrows step, a separator a reader hears, while the table reports the order and the width and the app keeps them, as it keeps the sort. A column whose width the layout decides has no edge to drag. |
| `TreeSliver`, `TreeSliverNode`, `TreeSliverController`, `onNodeToggle` | `TreeView` and its `TreeNode`s, a `Navigable` whose role is `Tree` over `TreeItem` pressables that state their `TreePlace` | **SAME, and further.** The shape is Flutter's: the VISIBLE nodes are one flat list of rows, the tree owns the indentation and which nodes are open (started from the nodes' own flags, `ExpandedKeys` here), and a toggle is reported (`OnToggled`). Three things go further, each because Flutter leaves it to the app (#1530): the tree is read as a tree on every target, each item with its level and its place among its siblings, where `TreeSliver` adds no semantics of its own; it carries the WAI-ARIA tree pattern's keyboard, type-ahead included; and a node's children load through an async loader the first time it opens, with loading and error rows, where Flutter's app swaps the node's children itself. |
| `TableViewport`, `TwoDimensionalScrollView`, `TableView`, pinned rows and columns | `TableViewport` (places the cells it is handed, pins the leading rows and columns, scrolls both axes) and the `TableScroll` it carries | **PARTIAL.** The shape is Flutter's: one viewport per two axes, the leading bands pinned, a cell keyed by its position as a child is by its vicinity. Two things differ, each for a reason. The cells in view are built by the component above, from the viewport's reports, as `ListView` builds its rows, because no node builds during layout until the element kind `ELEMENT-TREE-PLAN.md` defers (§3.2). And the offset is the viewport's own on every target, the browser's scroll included, because a browser lays an element out at most 16 777 214 points tall and a million rows pass that. |
| `SingleChildRenderObjectWidget`, `MultiChildRenderObjectWidget`, `LeafRenderObjectWidget` — the SHAPES a node can take, named once | `SingleChildNode` names the first; `FlexNode` covers the flex containers only; the leaves share no base | **PARTIAL — one shape of three.** `SingleChildNode` holds the thirty-two nodes whose child is REQUIRED, so "a layout-transparent wrapper" is a type the compiler knows rather than a list each realizer keeps. `Box` is deliberately not one: its child is optional, and a base meaning "wraps a child" would have to make `Child` nullable for all thirty-two to admit the one. The other two shapes are still unnamed — `FlexNode`, `Grid`, `Stack` and `Navigable` each hold many through a collection of their own, and the eleven leaves are leaves only by having no child property. |

## 2. Layout, constraints and rendering

| Flutter | Here | Verdict |
|---|---|---|
| "Constraints go down, sizes go up, parents set positions" | The same discipline, single pass | **SAME** in behaviour. |
| `BoxConstraints` as a VALUE (`tight`, `loose`, `bounded`, `unbounded`) | `BoxConstraints` in `Primitives`, an author's value: `Tight`, `Loose`, `IsTight`, `HasBoundedWidth`, `HasBoundedHeight`, `Biggest`, `Smallest`, `Constrain`, `Enforce`, `Loosen`, `Deflate`; `ConstrainedBox` applies one | **SAME.** An unbounded maximum is `float.PositiveInfinity` and the default is unbounded, as Flutter's is, so it is a class and not a struct, whose default would be a box tight at zero. The engine still measures with a record of its own, `LayoutConstraints` / `AxisConstraint`, whose flags say who decided a size and whether a stretch survives an INLINE boundary (a `Pressable`, an `Adjustable`, a `Link`), which one of our two targets answers to CSS for: that is the engine's policy and the web could produce none of it, so it stays in `Native.Framework` and is projected onto the author's value in one place (`LayoutConstraints.FillingRoom`). `ConstrainedBox` is a `Box` with the value's bounds, which follow CSS: a stated maximum wins over a parent's stretch, where Flutter's `enforce` keeps the parent's tight width (#1555). |
| `Rect`, `Offset`, `Size` in `dart:ui` — geometry UNDER everything | `Rect`, `Point`, `Size` in `Primitives` — geometry under the vocabulary | **SAME, after the move.** They were in `Native.Engine`, above the vocabulary, where only Photon could reach them, and the cost was paid three times over: `ICanvasPainter` spelling every box as four floats, `SemanticNode` unable to move down because it carries a `Rect`, and `LayoutConstraints` (#119) born in `Native.Framework` where no `LayoutBuilder` can hand it to an author. The move itself cost three edits — two `using` lines and one qualified name — which is the measurement that says the placement was an accident of where the type was first needed rather than a dependency. The name stays `Point`: Flutter's `Offset` doubles as a vector and so does ours (`Dot`, `Length`), and `Point` is the word the rest of this SDK already uses. |
| `LayoutBuilder` | `LayoutBuilder(constraints => …)` | **SAME.** The builder is handed the `BoxConstraints` of the room its box has, a box that fills on both axes: the size the parent decides on each axis, unbounded where the box's size is left to what it holds, and no minimum. Photon runs it in the layout pass, as Flutter does, through a slot the realizer shows, and again only when the room or the node changes. The web cannot build inside the browser's layout, so it builds right after it, against the same room: the server writes the box empty, the browser measures it as if it held nothing and builds the child into it (#1555). The first external consumer's ruler, a `Canvas` whose paint callback did nothing, is this node now. |
| `CustomMultiChildLayout`, `MultiChildLayoutDelegate` | — | **GAP** |
| `CustomSingleChildLayout` | — | **GAP** |
| Subclassing `RenderBox` | — | **DIFFERENT by design.** The layout engine is closed; the vocabulary is the extension point. A consumer composes nodes rather than implementing `performLayout`, which is what keeps one component correct on both realizers. |
| `CustomPaint` / `CustomPainter` | `Canvas` + `ICanvasPainter` | **SAME**, and the painter already carries the box it was given. |
| `Canvas`, `Paint`, `Path`, shaders | The Photon engine's SDF shaders (Slang → Metal/SPIR-V) | **DIFFERENT.** Shaders are the ENGINE's, not an API. A consumer gets `Canvas` primitives; there is no `FragmentProgram`. Deliberate: a consumer shader would have to exist twice and match. |
| `TextOverflow.ellipsis` on `Text`, drawn by `TextPainter` in the neutral `painting` layer | `Text.MaxLines`; the mark is INSIDE the measurement — CoreText truncates in its own layout (#123; the middle-cut of `.53` fixed in #136), Android's measurer appends it, CSS draws it on the web; DirectWrite still cuts without one | **PARTIAL — three of four targets.** Flutter puts the mark in one neutral painter; we put it where each platform makes the line, so the rule the contract states (the glyphs drawn are the line measured) is honoured at three sites today and by three different hands: CoreText's and Android's measurers shape it themselves, the web leaves it to the browser through CSS `text-overflow` (the browser is the shaper there, and `ITextMeasurer` is not on that path), and DirectWrite cuts without it. `TruncationContractTests` asks every measurer it can host, and carries DirectWrite as withholding until `SetTrimming` is verified on a Windows box. `MeasuredLine.Ellipsized` remains `didExceedMaxLines`'s analogue, read by no realizer. |
| `Transform`, with a `Matrix4` | `BoxStyle.Transform`, a `Transform2D` (translate, rotate, scale) applied around the box's centre, and `StyleDiff.Transform` for a state | **PARTIAL.** Two-dimensional and centre-anchored: there is no `alignment` or `origin` to move the pivot and no perspective. Paint-only on both targets, so layout never moves. A state's transform REPLACES the base's, the way a CSS rule replaces `transform`: a card rotated at rest and lifted on hover states both in its hover transform (#507). |
| `Align` with an `Alignment`/`FractionalOffset`, and `FractionalTranslation` | `Positioned` with `TopFraction`, `StartFraction`, `EndFraction`, `BottomFraction` (a fraction of the stack plus a point offset) and `ShiftX`/`ShiftY` (a fraction of the child's own size) | **SAME** in what it can place. One node carries both, where Flutter composes two widgets; a shift moves only that child, never the stack's other children or its size (#636). A paint-only twin a state can change is `Transform2D.FractionalTranslate`, a fraction of the box's own size added to its translation (#614). |
| `SliverGridDelegateWithMaxCrossAxisExtent` | `GridTrack.AutoFill(min)`, the grid's whole column list | **DIFFERENT.** Flutter bounds a column's MAXIMUM width; this bounds its MINIMUM, as CSS `repeat(auto-fill, minmax(min(min, 100%), 1fr))` does, and Photon computes the same count; in a grid narrower than one track both draw one column of the grid's width. An auto-fill track stands alone (#636). |
| `SvgPicture` with `width: double.infinity` | `Drawing(artwork, SizeValue.Fill)` | **SAME.** The height follows the artwork's aspect, or a given `height` (#636). |
| `DecorationImage` on a `BoxDecoration` (`repeat`, `alignment`, `fit`, `opacity`) | `BoxStyle.Patterns`, a list from a closed set: `DrawingPattern` (a `VectorDrawing`) and `ImagePattern` (an image source) under `ArtworkPattern`, beside `GridPattern`. `HorizontalRepeat`/`VerticalRepeat` (`TileRepeat`), `Anchor` with an `Offset`, `Fit`, and `Opacity` on the drawing | **SAME** in shape, and wider: what the CSS backgrounds model gives a page enters too, on Photon as on the web. That covers spaced and fitted repetition, the area the tiles are placed in and the one they are clipped to (`BoxArea`), a window attachment (`TileAttachment`) and several layers in one box. Photon draws each layer in one repeating command, at the exact period and phase (#1937). Fenced: `centerSlice`, which is `Image`'s own nine-slice fence, and `scale`, a raster's density, since a tile is sized in dp. An image tile has no opacity, because a CSS layer has none; the image carries its own transparency. |
| `WidgetStateProperty` (`resolveWith` over hovered, focused, pressed, …) | `StyleDiff`, a partial style per state: `BoxStyle.Hover`, `BoxStyle.Focus` and `BoxStyle.Pressed`; a pressed fill is the `Pressed` diff's `Background` on the box it fills (#616) | **DIFFERENT.** Flutter resolves each PROPERTY against the set of states a control is in; we resolve each STATE to a diff laid over the base. For a fixed order of states the two say the same thing, and a diff is what the web writes as one rule and Photon as one overlay. The OWNERS match Flutter's: a hover, a focus and a press are the control's (the `Pressable`), shown by every box inside it up to a control nested in it, in the handoff's order, pressed over focus over hover, on both targets (#508, #616, #614); a box outside every control hovers itself. Every member of a diff applies, and a state rewrites the lists it shares with the base (the shadows, the background layers) rather than replacing them (#507). `DefaultTextStyle` and `IconTheme`'s colour is `BoxStyle.Foreground`, which a state's diff can change: a text, an icon or a vector with no colour of its own takes the nearest box's (#614). |

## 4. Animation

| Flutter | Here | Verdict |
|---|---|---|
| `AnimationController` + `TickerProvider` | `IFrameTicker`, `LoopMotion`, `Presence`, `TransitionClock` | **DIFFERENT, and this is the deepest divergence.** Flutter's animation is IMPERATIVE — you hold a controller, drive it, dispose it. Ours is DECLARATIVE: a style diff plus a motion token, and the host interpolates. A component says what it looks like in each state, never how to get there. That is why there is no controller to leak and no `dispose` to forget. |
| `Tween`, `ColorTween`, `Matrix4Tween` | — (the engine interpolates) | **DIFFERENT** — the consequence of the row above. Nothing holds a tween because nothing drives one. |
| `Curves` | `Curve`, a cubic's four control points (`Standard`, `Decelerate`, `Accelerate`) + `Motion.Fast/Base/Slow` | **SAME**, on a fixed ladder: 100/200/300 and nothing between the rungs. A curve is one value on every target, as a `Cubic` is: the web hands it to CSS as `cubic-bezier()`, and Photon evaluates it with `CurveEvaluator`, which stays on the host (#518). |
| `AnimatedContainer` and the implicit family | `TransitionSpec?` — a `Transition` on the style, on `Text` and on the pressed/hover diffs | **SAME idea, smaller surface.** A property on the things that change rather than a parallel type per animatable property. |
| `AnimatedBuilder` / `AnimatedWidget` | — | **GAP** (imperative-only concepts) |
| `Hero` / shared element | — | **GAP** |
| `SpringSimulation`, `FrictionSimulation` | `SpringSpec` (stiffness, damping, mass) | **PARTIAL** — the spring is specified and used by gesture release; the other simulations are absent. |

## 5. Gestures, pointer and focus

| Flutter | Here | Verdict |
|---|---|---|
| `Listener` — raw pointer events | `Listener`: `OnPointerDown`, `OnPointerMove`, `OnPointerUp`, `OnPointerCancel`, `OnPointerHover`, `OnPointerScroll`, each with a `PointerEvent` in its own box | **SAME.** A wrapper over any node hears the pointer in its own coordinates, with its kind, its buttons (Flutter's constants) and the keys held, followed from its down to its up or its cancel wherever it goes, and it only listens, as Flutter's does: what it holds still presses and scrolls (#1562). `Canvas.OnPointerDown/Move/Up` stays the drawing surface's own. Photon reports one pointer, as its shells deliver one, and a secondary click as its down and its up at once. |
| `HitTestBehavior` | `Listener.Behavior`: `DeferToChild`, `Opaque`, `Translucent` | **SAME** in its rule, Flutter's, written for the web over the browser's own hit test and for Photon over the frame's paint, and both run the same cases (`listener-hits.fixture.json`, #1562). A child is hit where it draws or answers, and a fill that paints nothing draws nothing: Flutter's transparent `Container` is `Opaque` here. One trade: a behaviour decides which LISTENERS hear, never who takes a press, so an opaque listener hides the listeners behind it and not a button, because the web delivers a press to one element and a listener must not take it. |
| `GestureArena`, competing recognizers | `GestureArena` and `GestureRouter`, written once in the vocabulary and run transpiled in the browser; the SDK's own gestures are members | **PARTIAL.** Flutter's rule, run by both targets from one source and pinned by one fixture (`gesture-arena.fixture.json`): a member that accepts while the arena is open wins when it closes, a lone member wins at the close, the last one left wins, and at the up with nothing decided the first member, the innermost, wins; a cancel takes the pointer from every member. The press, the drag, the sort, the context hold and the pans are members, each keeping its own arming, so they resolve among themselves as they always did (#1563). PARTIAL because an arena cannot be held open past the up (Flutter's `hold`, for a double tap), it follows one pointer, as the shells deliver one, and a field, a code surface and a sheet surface are not members: they take the press and its selection at the down, and the web has no cancel for a native field's selection. |
| `GestureDetector` | `Pressable`, `Draggable`, `DragDismiss`, `Hoverable`, `Adjustable`, `Navigable` | **DIFFERENT, and better for this SDK.** Flutter has one detector with twenty callbacks; we have a node per INTENT, which is what lets each one carry its own semantics — a `Pressable` states its own accessible name and selection, a `Draggable` its axis and limits. |
| `RawGestureDetector`, custom recognizers | `RawGestureDetector`, a `GestureRecognizer` the app subclasses in C#, and `GestureRecognizerFactoryWithHandlers<T>` | **DIFFERENT.** Flutter's names and Flutter's protocol: the recognizer hears the pointers it allows, asks for them with `Resolve`, counts a deadline, and outlives a rebuild, initialized by each build's factory and made again when the factory changes type (`canUpdate`). On Photon the arena is Flutter's whole, a scroll view's pan included: a recognizer that accepted first, a hold, keeps the list from moving. The browser's scroll is a member the arena cannot hold: it pans by its own slop and says so with `pointercancel`, which rejects every member, so a recognizer takes the pointer from it only by accepting before it pans, as a hold always can; and a press that lost has its `click` swallowed, where Flutter never fires it. |
| `MenuAnchor`, `ContextMenuController`, `onSecondaryTap`, `onLongPress` | `ContextTarget`, `ContextMenu`, `Anchored.At` | **PARTIAL.** A context request is a node per intent, as the rest of the gestures are: `ContextTarget` wraps any node and hears a secondary click, a finger's hold, the menu key and Shift+F10 on every target and shell, the innermost one answering, with the point in its own box (#1531). `Anchored.At` opens a panel at that point, as `MenuAnchor` takes an offset, and `ContextMenu` is the composition over the `Menu`'s panel. PARTIAL because a reader's own "show menu" action (VoiceOver's, TalkBack's) is not offered yet, a panel does not flip at the viewport's edge, and a composite whose focus is its active descendant (a tree, a grid) does not route the menu key to the active item. |
| `FocusNode`, `FocusScope`, `FocusManager` | `InitialFocus`, the focus route, `Navigable` | **PARTIAL** — focus order and initial focus are expressible; there is no focus object to hold or move imperatively. |
| `InkWell.canRequestFocus` | `Pressable.CanRequestFocus` | **SAME.** A control pressed while the keyboard stays where it is: a row of a code editor's completion list, a formatting toolbar's button. The web cancels the press's focus move and keeps the control out of the Tab order; Photon ends no editing, focuses nothing and makes no Tab stop of it. |
| `RawAutocomplete`: `optionsViewBuilder`, `AutocompleteHighlightedOption` | `CodeSurface.Options`, `OptionsOrigin`, `HighlightedOption` | **DIFFERENT.** Flutter draws the options in an overlay that a `CompositedTransformFollower` keeps glued to the field. Ours are drawn by the code surface itself, in the code's own coordinates, so they move with the code as it scrolls, and the input they belong to names them and points at the highlighted one (`aria-controls`, `aria-activedescendant`). The price is the editor's viewport: the list stays inside it, where an overlay would escape it (#297). |
| `TextEditingController` + `EditableText` — the WIDGET owns the editing protocol; `TextInput` only bridges the platform's keyboard | `CodeEditorController` (in its own `eQuantic.UI.Code`) and `SheetController` (in its own `eQuantic.UI.Sheet`) own their editors' protocol behind the vocabulary's `ICodeSurfaceModel` and `ISheetSurfaceModel`: what a key, a text or a pointer MEANS, and where every caret, band and cell is, are their answers, and both hosts only forward events (and paint a code surface's carets) | **PARTIAL.** Both editors took Flutter's road (docs/CODE-EDITOR-PLAN.md, #185); the text field's IME and focus are still per host. |
| `TextInputClient`, `TextInputConnection` — the phone's keyboard hands the field its whole new `TextEditingValue`, never keys | `PhotonHost.EditingValue` and `UpdateEditingValue`, `TextEditingValue`, and `TextInputSession`, which the Android and iOS shells only translate | **SAME.** A keyboard that autocorrects, suggests, swipes or dictates edits a document, so the field's text, selection and composing range cross whole, in both directions, with Flutter's names. The composition is IN the text, as in Flutter and on the web, and the app hears the word as it is typed. The session is polled after each frame instead of being attached by the field, because the focus is the host's. A code surface and a sheet stay on the desktop's path, keys and committed text: their text is their controller's, not a document the keyboard could autocorrect (#770). |
| `Shortcuts` / `Actions` | `Shortcut` + `KeyChord`; `Shortcut.FocusScoped` | **DIFFERENT.** Flutter's shortcuts answer for the focus: a key travels up from it, and an app-wide one sits at the root. There is no `Intent`/`Action` indirection: a chord calls its handler. |

## 9. Accessibility, i18n and platform adaptation

| Flutter | Here | Verdict |
|---|---|---|
| `Semantics` tree for screen readers | Our own semantics walk + the macOS/iOS/Android bridges | **SAME.** Worth recording how thin the ice was: six of the fourteen labelled nodes reached no bridge at all until the walk was enumerated by reflection rather than maintained by hand. |
| `SemanticsNode`, `SemanticsConfiguration` — in `package:flutter/semantics`, beneath every target | `SemanticRole`, `SemanticNode` — in `Primitives`, beneath every target; only the native realizer produces them, and the web decides the same things inline | **PARTIAL, and the fault has moved.** It used to be the LOCATION: the one answer with a type sat in one target's assembly, where the other two could not reference it. That half is done — the move cost three `using` lines, the same measurement the geometry move gave. What remains is that only ONE realizer speaks the type: the web writes ARIA inline, and could now stop. The probe asserts both halves, so the row comes off PARTIAL when the second one lands rather than when someone remembers. Since #976 a node is named by an integer `Id` its position keeps from mount to unmount, as a `SemanticsNode.id` lives as long as the render object that made it, and the three bridges activate and adjust by it. |
| `SemanticsRole.table`, `row`, `cell`, `columnHeader` | `TableRole` on the table viewport and `TableCellRole`, `Selected` and `Current` on its cells; `SemanticRole.Table`, `Grid`, `Cell`, `ColumnHeader` and `RowHeader` on Photon | **PARTIAL.** The roles, each cell's place and the whole grid's extent reach both realizers (#1081), and where Flutter stops at a column header both ARIA and AppKit also name a grid and a row header, so this vocabulary does. The web's rows own their cells by `aria-owns` across the pinned bands; Photon's tree is flat, so a row holds nothing there until #1105 nests it. |
| `Semantics(liveRegion: true)`, `SemanticsService.announce` | `LiveRegion`, and a surface's own words (`SheetSurface.Announcement`) | **SAME, since #1081.** A region that changes is posted on macOS, iOS and Android; on Android its node is marked live and its content reported changed, the route Flutter takes since Android deprecated announcement events. A change inside the one-second quiet window is said when the window ends, with the region's text then. |
| `MergeSemantics`, `ExcludeSemantics` | `MergeSemantics` and `ExcludeSemantics`, the same two words, and `Text.ExcludeFromSemantics` for one paragraph | **SAME, since #1567.** A merge is one stop: the first control in it, named by everything the subtree says, or a group named the same way when nothing in it is a control, and a later control stays a stop of its own. On the web the parts are hidden and the stop names itself by them with `aria-labelledby`, so the name is the browser's to compute and follows the content. An exclusion is passed over on every bridge, as Flutter's is, controls included, and `Excluding` turns it off without changing the tree. |
| `Semantics(namesRoute: true)` around a dialog's title, `InputDecoration`'s `label` and `helper` merged into the field's node | `LabelPart` and `DescriptionPart`, which name and describe the nearest dialog, group, live region, field or check they reach | **SAME, since #1916**, and one word wider: Flutter's flag names a route and its decorator names the one field it wraps, where a part names whichever nameable it stands beside. A part reaches the nearest nameable container, or the one control a node holds that no nearer part reached and that names nothing itself, and a node holding two is refused with one sentence on every target. On the web the nameable lists the parts' ids in `aria-labelledby` or `aria-describedby`, so the name follows the part's text; on Photon its stop is named by the text under the parts and carries their description. |
| `Localizations`, `LocalizationsDelegate`, `Intl` | `.resx`, `CultureInfo`, `ICultureController`, culture routes | **DIFFERENT, and deliberately .NET's.** Localization is done the way .NET does it, not the way Flutter does it — a .NET developer already knows this API. |
| `TextDirection.ltr/rtl` | `TextDirection`, `Directionality`, `ComponentContext.TextDirection` | **SAME for the web, since #1568.** A subtree reads the nearest `Directionality` above it, or its UI culture's direction from .NET, and the web writes every start and end as logical CSS under the page's `dir`, so an Arabic page mirrors. Since #1569 what only the SDK knows follows it too: a glyph that matches the direction, a drag, a sortable list, the arrow keys and a horizontal scroll offset all read "toward the end" and "from the start" in the page's direction. Photon reads the direction and still lays out left to right, and binds the arrow keys and drags physically. |
| `IconData.matchTextDirection` | `IconGlyph.MatchTextDirection`, set on the curated `ChevronLeft` and `ChevronRight` | **SAME for the web, since #1569.** A glyph that sets it is drawn as it points in English and turns where its element reads right to left (`scale: var(--eq-inline, 1) 1`), so a back link needs no choice from `context.TextDirection`; a glyph without it never turns. Photon draws every glyph unmirrored until it mirrors, which stays outside 1.0. |
| `ThemeData` vs `CupertinoThemeData` | One `IAppTheme` + `Density` read from the TARGET | **DIFFERENT, and better.** Flutter asks the author to pick a design language per platform and then reconcile two theme objects. We have one theme, and the density that makes a Mac toolbar tighter than a phone's comes from the target, never from the call site. |
| `MediaQuery` insets, notch, `devicePixelRatio` | `SafeArea`, `WindowChrome`, window size classes | **PARTIAL** — insets and size classes are expressible; there is no single query object. |
| `MediaQuery.viewInsets`, `Scaffold.resizeToAvoidBottomInset` | `PhotonHost.ViewInsets` | **SAME** in what a screen does: the tree lays out above the keyboard, as a `Scaffold` does by default, the safe area under it counts once, as Flutter's padding does under its view insets, and a frame laid out shorter than the last scrolls the field being edited into view, as `EditableText.didChangeMetrics` does. One step past Flutter: where nothing scrolls, Flutter's column overflows and leaves the field under the keyboard, and the host lifts the screen until the field shows, as Android's `adjustPan` does. What is not reproduced is the query: a component cannot read the inset, which is the `MediaQuery` row above (#770). |
| `TextField.keyboardType`, `TextInputType`, `autofillHints` | `TextEntry.Kind`, a `TextEntryKind`: `Text`, `Email`, `Phone`, `Url`, `Number`, `Decimal` | **DIFFERENT.** Flutter names the keyboard and lists the autofill hints apart; here the field says what it TAKES, and each target derives the keyboard, the autofill and whether the text is prose from it: `inputmode` and `autocomplete` on the web (never `type="email"`, which refuses the selection API), `keyboardType` and `textContentType` on iOS, `inputType` on Android. A hint a kind does not imply, a name or a postal code, is a GAP (#1762). `TextInputType.numberWithOptions(signed: true)` has no kind: iOS's number pads have no minus (#1761). |
| `InputDecoration.prefixText`, `suffixText` | `TextInput`'s and `FormInput`'s `prefix` and `suffix` | **SAME**, with one step past it: the affixes are part of the field's accessible name (`Price (€)`), where Flutter's are read only as text beside the field. `MoneyInput` and `NumberInput` are built on them, with what Flutter leaves to `intl`'s `NumberFormat.currency`: the amount written and read in the culture, the currency's symbol on the side the culture puts its own (#1764). |

## What this adds up to

**One gap explained several others.** There was no Element tree, so there was no position to look up
from, so there is no `InheritedWidget`, no `didChangeDependencies`, and no dependency-driven rebuild.
That was one decision to take, not four, and it was taken on 2026-10-14: the Element is built before
1.0, in the slices of [ELEMENT-TREE-PLAN.md](ELEMENT-TREE-PLAN.md), and each flips the rows it closes.
The first slice gave Photon the tree (#950); the lookup up it, which the three rows wait for, is E5's.

**The two gaps that had a consumer blocked behind them are closed**, and a blocked consumer is the only
evidence that counts here: `LayoutBuilder` (a child built against its own box) and the authorable
constraint type that goes with it, `BoxConstraints` (#1555).

**No PARTIAL row is about WHERE a thing lives any more.** Both were: `Rect` above the vocabulary,
and `SemanticsNode` inside one target instead of beneath all of them. Both are moves rather than
features, both cost about three `using` lines, and both are done.
[ARCHITECTURE-AUDIT.md](ARCHITECTURE-AUDIT.md) carries the measurements behind them —
including what the first of them turned out to have been causing.

**Three DIFFERENT rows are the ones to keep and defend**, because they are where this SDK is not a
smaller Flutter: declarative animation with no controller to leak; typed capabilities instead of
method channels; and a route that is an attribute rather than a table. Each of them is a direct
consequence of the product principle — the developer writes C# and never learns a platform artifact.
