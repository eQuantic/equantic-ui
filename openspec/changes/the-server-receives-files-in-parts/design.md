## Context

A Server Action is one JSON request of at most 1 MB, and the browser hands a page a file's content, never its path. A file of real size has to reach the server in parts, survive a dropped connection or a restart in the middle, belong to the person who sent it, and end up in the app's own Server Action, where the app stores it. myartwork3d proved the shape in an app (`MyArtwork3D.Web/Uploads`): tus through `tusdotnet`, an owner by sign-in or by cookie, a record beside the bytes, a sweep of what expired. This slice makes it the SDK's, behind a C# declaration.

## How Flutter answers it

Flutter has no server and no upload of its own: `file_picker` hands the app the bytes or a stream, and the app sends them with `http`'s `MultipartRequest` or `dio`'s `FormData`, writing the transport itself, and a resumable upload is a third-party package (`tus_client_dart`) speaking tus to a server the app runs. The SDK owns both ends here, so it takes the protocol Flutter's ecosystem reaches for when an upload must resume, and keeps it off the developer's page: the developer declares a policy and receives an `UploadedFile`, and neither the protocol nor its library is named.

## Decisions

- **tus 1.0 through `tusdotnet`, every type of it internal.** A resumable protocol with an offset to resume from, an expiry and a server library that has served it for years beats a home-grown chunked POST. `tusdotnet` 2.12.0 is the latest stable, runs on net10 through its net6.0 build with no further dependency, and nuget.org lists no advisory against it. The endpoint offers creation, creation-with-upload, termination, expiration and checksum, and not `creation-defer-length` (a policy weighs the size when the upload starts) or `concatenation` (parts concatenated into a file no creation declared): the engine refuses those itself.
- **Registered as the server events are.** `UseUploads(Action<UploadsBuilder>)` on `UIOptions` registers its services and its endpoint once however many times it is called, `UploadsBuilder.Accept` refuses a second policy of one name and takes the same policy twice once, and `UploadsOptions` binds `EQuantic:Uploads` with a validator that stops the app at start on a limit it cannot run with (no unfinished upload allowed, an expiry of zero or past the 400 days a browser keeps the cookie).
- **The owner: `user:<id>` or `visitor:<id>`.** The signed-in person's `ClaimTypes.NameIdentifier`, else `sub`. A visitor is named by a random 128-bit id in the `eq-uploads` cookie: HttpOnly, SameSite=Lax, Secure over HTTPS, essential (strictly necessary for the upload the person asked for, so it needs no consent), written when the upload's record is, and written AGAIN by each upload with the expiry as its lifetime, so it outlives every upload it names. A lifetime counted from the first upload would end in the middle of a later one, which would then belong to nobody.
- **A record beside the bytes.** `<id>.upload.json` holds the owner, the policy, the file's name without any folder the device sent, its MIME type, its size, when it started and when it expires. The records are read back the first time the server is asked about an upload, so the owner and nobody else continues one after a restart; a record whose bytes are gone, or whose id is not its file's name, is dropped. The records live in memory once read, so the store serves one instance of the app; several instances each know only the uploads they received.
- **The unfinished count is atomic.** A creation holds a place among its owner's unfinished uploads from the moment it is accepted until its record is written, under one lock with the records and the set of finished ones, so twelve creations sent at once by one owner make exactly the allowed number (measured).
- **The folder is staging, and the server sweeps it.** A hosted service removes every upload past its expiry, finished or not, at start and every ten minutes, on the app's `TimeProvider`. `tusdotnet`'s own expiry removes only unfinished uploads (measured: of an expired finished and an expired unfinished upload, `GetExpiredFilesAsync` lists the second alone), so the sweep removes by the records first and lets the engine's sweep take what no record names.
- **The origin check is the actions' own.** `AllowedRequestOrigins` holds the `ServerActionOrigins` rule over `EQuantic:ServerActions:AllowedOrigins`, refreshed on a configuration reload, and both the actions middleware and the upload endpoint ask it.
- **Binding: the id alone, through a server subclass.** `UploadedFile` is a public, non-sealed class whose `OpenRead` and `Delete` are virtual, `[ServerOnly]`, and throw for a value the page built. The middleware binds an `UploadedFile` parameter from the argument's `id` and nothing else, refuses it for another owner (403), an unknown or expired upload (404) or an unfinished one (409) with the actions' failure shape before the action runs, and hands the action an internal sealed subclass whose members read the store. The vocabulary assembly grants no `InternalsVisibleTo`, and an internal seam would have needed one; a virtual member overridden on the server leaks nothing an app can use, since only the server makes the subclass. The `[ServerOnly]` fence already walks overrides, so client code calling either member is refused at the build (EQ2010).

## Risks / Trade-offs

- One instance: a balancer that sends the parts of one upload to two instances refuses the second instance's parts until the store is shared (a later change, with a backplane for the records).
- A person who signs in during an upload loses it to their visitor id, since the owner changes. The page starts it again.
- The PATCH bodies are held to Kestrel's own request limit (30 MB by default), so the client sends parts below it; slice C chooses the part size.
- A request from an origin the app allows for its actions may upload too, and a page on another domain also needs the app's CORS policy to expose the tus headers, which this slice does not configure.
