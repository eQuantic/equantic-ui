## Context

The upload endpoint (#1214) speaks tus through `tusdotnet` and keeps every upload in one folder: the engine's `TusDiskStore` holds the bytes and its side files, and `UploadStore` writes each record beside them and holds every record, the finished set and the limits' tallies in memory, read once from the folder. That makes the truth one instance's. The client (#1215) starts an `Upload` per chosen file, all at once.

## How Flutter answers it

Flutter has no server: `file_picker` hands the app the bytes, and the app sends them with `http` or `dio`, choosing its own concurrency (`Future.wait` over a list sends all at once; a pool package or a loop bounds it) and its own storage on its own server. The SDK owns both ends here, so it bounds the concurrency itself and leaves the storage to the app behind a seam, as it already does for the server events' backplane.

## Decisions

- **A seam of the SDK's own, not the engine's.** `tusdotnet`'s `ITusStore` family is six interfaces of protocol vocabulary (an Upload-Metadata string, an expiration store, a checksum store) and would put the library on the public surface. `IUploadStorage` has seven members in the SDK's words: `CreateAsync(StoredUpload)`, `FindAsync(id)`, `LengthAsync(id)`, `AppendAsync(id, offset, content)`, `OpenReadAsync(id)`, `DeleteAsync(id)` and `ListAsync()`, each with a `CancellationToken` and answering a `ValueTask` as `IServerEventBackplane` does. An internal adapter is the engine's store over it, so the engine, the binding of a Server Action and the cleaner all read one storage, the default included: one path, exercised by every existing test.
- **The record is public.** `StoredUpload` (the id, the owner, the policy, the file's name, its MIME type, its size, when it started and when it expires) is what a storage persists, so it is a public sealed record, the internal `UploadRecord` it replaces. The owner is an opaque string to a storage.
- **What a storage must guarantee, and nothing more.** `AppendAsync` adds the content at `offset` only when that is the length it holds, and otherwise keeps nothing and answers 0, so two instances that both accepted a part for one offset (a retry that overlapped the request it retried) cannot write it twice: the engine's own lock is per instance. An append that is cut off may keep all, some or none of what arrived, in order, as long as `LengthAsync` then answers what it kept; the client asks for the offset before it sends again. An S3 storage writes each part as an object of its own and reads them in order; a database appends a row; a folder appends to a file.
- **The server hands a storage only the ids it gives.** The engine's ids are 32 lowercase hexadecimal digits; the store answers any other id (a path, `..`) as an upload that does not exist without asking the storage, which keeps a storage over a folder or a key space from being led anywhere by a request.
- **The limits read the storage.** Each creation lists the storage and counts, per owner and for the whole store, the uploads and their declared bytes, and the owner's unfinished ones by their lengths. The places a creation holds until its record is written stay in the instance's memory, under a lock that covers the listing and the check, and a place that already has its id is not counted twice beside the record it wrote: twelve creations sent at once to one instance still make exactly the allowed number. Across instances, creations that arrive at the same instant on different instances may each take the last place: the limits bound abuse, and the excess is bounded by the number of instances.
- **The expiry reads the storage.** The cleaner lists it and deletes every upload past its expiry, finished or not. The engine's expiration asks the record's expiry. The engine's own sweep had a second job, the bytes of a creation stopped before its record was written; the record is now written in the same step the upload is created in the storage, so there are no such bytes.
- **The folder stays the default, for one instance.** `FolderUploadStorage` keeps `<id>` and `<id>.upload.json` in the folder `EQuantic:Uploads:Folder` names, an index of the records in memory read once (it is the only writer of its folder), and the lengths from the file system. An append opens the file alone and appends only at its length. A record whose bytes are gone is dropped when the folder is read, as before.
- **Two extensions go.** `creation-with-upload` would append before the record exists, and `checksum` was the disk store's; the SDK's client sends neither. The endpoint offers creation, termination and expiration, and still refuses `creation-defer-length` and `concatenation`.
- **Three at a time, page-wide.** A module-level pool in the runtime gives each `Upload` a slot before its first request and takes it back when it completes, fails, is paused or is cancelled; a waiting upload is `Waiting`, the state a new upload already starts in. Three keeps a phone's connection busy without starving the page, and stays under the server's default of five with room for a second tab.
- **The first creation goes alone.** A visitor's browser is named by the cookie the server writes with its first upload; three creations sent together before it each made a visitor of their own, the browser kept the last cookie, and the other two uploads were answered "This upload belongs to someone else." at their first part (seen in the sample's browser while proving this change; the client that started every file at once had it too). The page's turns hold one slot until the server answers a creation or an offset, and then open to three. A signed-in person waits one request for it.
- **`Retry-After` marks what frees itself.** The server sets it, five seconds, only on the owner's unfinished limit. The client reads a 429 that carries it as a wait, keeping its slot, and gives up after ten minutes with the server's reason; abandoned unfinished uploads (a closed tab) free their places only when they expire, and a person should not watch a row wait for a day.

## Risks / Trade-offs

- A storage that lists slowly makes every creation slower: `ListAsync` is read on each creation and every ten minutes. The docs say so; a storage over a database answers it with a query.
- The excess across instances described above.
- A folder written by an earlier version keeps the engine's side files until they are removed by hand; they are a few bytes each, and their uploads expire.
