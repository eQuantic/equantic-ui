# Proposal

Closes #1416, a Bug under #1174.

## Why

`scripts/generate-shaders.sh` handed `slangc` the shader source's absolute path, so every `#line` directive of the
committed `Sdf.metal` that names the source named the directory of the machine that generated it, a home folder
included. The committed file named one person's machine, and every contributor who regenerated the shaders got a
diff of path lines that said nothing about the shader.

## What Changes

- The generator runs `slangc` from the shader's folder and hands it the source by its name, `Sdf.slang`, so a
  `#line` names the source relative to the shader. The directives stay, since a Metal compile error still points at
  the Slang line.
- The committed outputs are regenerated by the script: `Sdf.metal` changes in its two `#line` paths alone, and the
  SPIR-V comes out byte for byte the same.
- `GeneratedShaderPathTests` fails when a generated shader, text or binary, names a path only one machine has, and
  when a `#line` of the Metal source names a rooted path.
- No app behaviour, public surface or developer surface moves: the shader is the same shader. No capability's
  requirements change, so this change carries no spec delta.

## Impact

`scripts/generate-shaders.sh`, the committed `Shaders/Generated/Sdf.metal`, and a test in
`eQuantic.UI.Native.Engine.Tests`. The metallib is not regenerated on a machine without the Xcode Metal Toolchain,
which the script says; it carries no path, which the new test reads.
